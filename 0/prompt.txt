  **datasquare design summary**
  
  The project is a Next.js/TypeScript talent background-check and search engine. The core code is in `/Users/aisandbox/Documents/datasquare/src/lib/talent-audit/` and `/Users/aisandbox/Documents/datasquare/src/lib/tools/`. I found no Crustdata, DBLP or news sources in the code.
  
  **1. Data sources and how each is queried**
  - **ORCID:** public API with an OAuth token that is cached. Search runs in 3 stages: name + affiliation, then name only, then full text. Each stage tries both name orders. It then pulls employments, educations and works.
  - **OpenAlex:** author search by name, a direct lookup by ORCID, and top-cited works per author. Since Google Scholar Profiles went away, OpenAlex is the main source for metrics.
  - **Google Scholar:** profile and author lookups through SerpAPI.
  - **Semantic Scholar** and **AMiner** clients.
  - **Crossref:** papers by DOI or title.
  - **Wikipedia, Baidu Baike, institution pages.**
  - **Open web:** LLM search grounding first, then the Bocha API, then DuckDuckGo.
  - **Internal entity library:** manually verified records.
  - The academic, ORCID, wiki and web stages run in parallel. A planning pre-stage ("Stage 0") picks the English name and fields, and may recall an ORCID that is then checked.
  
  **2. Verification logic**
  - **Identity anchor:** a fingerprint built from the resume (name, English name, institutions, field, degree timeline, paper titles). Name-order variants are generated, e.g. "Shi Yigong" and "Yigong Shi".
  - **LLM judge per platform**, with strict rules: the same name is not the same person; one of institution, field or a representative paper must also match; a mismatched discipline means reject; when unsure, reject and say what is missing. It returns matched, confidence and a specific reason.
  - **Anchor rules:** a candidate needs confidence of at least 60 to be accepted. Same-person duplicate profiles are merged; namesakes are rejected.
  - **Strength levels:** 0 = none, 1 = name only, 2 = one platform, 3 = two or more platforms agree.
  - **Gate:** records whose subject does not match the anchor get `subjectAnchored=false` and are left out of corroboration.
  - **Deterministic scorer** (`disambiguation.ts`): multiplies weighted name, institution, field and co-author scores. Field uses embedding plus n-gram similarity; institution uses LCS and continuity; co-authors use Jaccard overlap; a softmax data-richness term is added. Confidence is "fallback" if the name match is below 0.9 and "low" if the gap to the second candidate is under 0.05 or no institution matches.
  - **Claims model:** each check records source, field, claim, what was found, verdict (support / contradict / insufficient / not_found), confidence and its basis, evidence URLs, timestamp and a SHA-256 digest.
  - **Card states** are counted by distinct sources, not records:
    - any contradiction: "conflicted", confidence ×0.5
    - 2+ sources: "corroborated", +10
    - 1 source: "single_source"
    - none: "unverified", confidence 0
  - **Source tiers:** authoritative, reference, open, derived.
  - **Paper check:** does the paper exist, is the person in the author list, does the author position match, and do the year and affiliation match.
  
  **3. AI answer structure**
  - The final synthesis returns JSON:
    - overall risk level and a short evaluation (max 150 chars) citing evidence
    - match / mismatch / manual_review counts
    - one item per claim: status, confidence band, source, method, the resume claim, evidence list, matched and mismatched fields, a short web excerpt, score
    - a `recheck` list of up to 3 items
  - **What it refuses to do:**
    - judge things the resume never claimed
    - use un-anchored data
    - call "not found" a mismatch (it becomes manual_review)
    - treat adjunct roles overlapping a main job as a conflict
  - Evidence gaps and failed sources are stated in the report and not blamed on the candidate.
  - Value scores are shrunk toward a prior mean based on evidence confidence: weight = 0.5 + 0.5 × confidence.
  
  **4. Prompt-design tricks**
  - Separate passes: identity judging, then per-source evidence gathering, then synthesis over structured claims (not raw logs), then a rule-based QA pass with no LLM.
  - The QA pass checks for single-source shown as multi-source, excluded subjects leaking in, "not covered" shown as mismatch, conflicts within one item, over-optimistic risk level, and a weak anchor.
  - Each pipeline step is judged pass/fail by code, not by the model. A failing step retries once. Items with no evidence are sent back for one extra targeted search (max 5).
  - Low temperature, JSON-only output, no inner double quotes, a quote-repair parser, and a degraded report if parsing fails.
  
  **5. Cost control**
  - ORCID token cache and a 5-minute in-process cache of the entity library.
  - "Search memory" in Supabase stores profiles and relations already rejected as namesakes, so they are not checked again.
  - Only the top 2 Scholar candidates get their papers fetched.
  - A token tracker with a price table records cost per stage; optional stages can be switched off.
  - Parallel stages, timeouts and fallbacks.
  
  **Apply to a PhD-advisor matching agent**
  1. Pin the advisor's identity (ORCID + OpenAlex + faculty page) before collecting any facts.
  2. Make the LLM judge give a specific reason; same name alone never counts as a match.
  3. Store each fact as a claim with source, URL, verdict and confidence.
  4. Count corroboration by distinct sources, and cut confidence when sources conflict.
  5. Treat "not found" as unverified, never as false; state the evidence gaps openly.
  6. Synthesize only from structured claims; forbid facts the student did not ask about.
  7. Run a deterministic QA pass, for example single-source shown as multi-source, or a stale affiliation.
  8. Cache resolved IDs and rejected namesakes, and track the cost of each API call.
